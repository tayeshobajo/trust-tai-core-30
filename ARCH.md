# Outreach Today architecture
Existing WorkspaceGate supplies user and organization identity. The panel uses React Query with user, organization and Chicago reporting date in its key. The existing member Supabase client performs metadata-only SELECT under RLS. A pure defensive projection rejects invalid/cross-scope records and holds conflicting provider identities. No send, sync, mutation or campaign qualification is introduced. Existing Comms consumers are unchanged.

# Comms architecture notes

See docs/architecture-canon.md for the project-wide contract. Comms owns its relationships, manual touches, stored provider messages and threads. React Query reads organization-scoped data through the member session. Provider ingestion is server-side and label-gated. Manual touches and provider messages remain separate records. UI attention is a derived reading, never a completion receipt. A message in one thread must not resolve an obligation in another thread or a manual due date.

Comms exact-message links use a separate member/RLS read constrained by organization, relationship and message ID. This avoids waiting for all historical email bodies, merges the target without duplication, and does not change provider ingestion or stored records. The bounded full-history read continues with a visible pending status. Direct relationship/message links open the mobile conversation pane.

Comms sync reliability (local candidate): read all existing approved-thread/message transport metadata with checked keyset pages, intersect approval and mailbox ownership, then rotate a bounded 25-thread batch using the integration cursor. Progress uses an updated_at compare-and-set so overlapping passes cannot overwrite later connection state. Transient errors remain retryable with capped backoff; only Google's explicit invalid_grant marks credentials revoked. Partial passes retain the previous success marker and expose unread/deferred counts; scheduled HTTP reports degraded/failed/deferred work as non-success. No ingestion label or grant changes. The relationship timeline uses newest-first timestamp/id keyset reads, displaying each page chronologically and offering older pages explicitly. Existing manually recorded obligations are unchanged.

Roadmaps stored-mail bridge: the canonical relationship binds the existing reviewed import and stored Gmail sources. Metadata-only scans are paginated and capped; only the requested newest page's bodies are selected. Exact mailbox/provider identity deduplicates sources, with reviewed redactions taking precedence. Roadmaps and Comms permissions and the binding are rechecked before release. Reads never invoke Gmail, create a relationship or infer a sale, booking or resolution. New provider ingestion requires the exact label on each message, including messages returned by stored-thread refresh.
